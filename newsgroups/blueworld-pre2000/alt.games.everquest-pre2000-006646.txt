Distributed process isn't just a marketing buzz.  Infact, if you're
using MFC, you have one such mechanism in place--it's called COM.  Try
invoking a COM server via the CoCreateInstanceEx() without putting
NULL in the COSERVERINFO parameter (no fair putting in your local
machine name)--your COM object to which you have an interface is
residing on a different machine while still "part" of the process
running on your local machine.  Magic!  :-)

>I'm sure each zone is in fact a separate thread.  

I *SERIOUSLY* doubt this.  I suspect each zone is in actuality a
seperate process (server process) running on possibly different
machines (some probably share machines which would explain why some
zones go down at the same time).

For one thing marshalling thread context across processes let alone
machines is a real pain in the ass (at least with COM anyways).

>It's very very easy to create multi-threaded code in Win32.  

Yep, and real easy to mess it up royally...

>I have no clue how they have their
>zones setup, but I'm sure each packet of information comming into the server
>is parsed and sent on to the proper thread for final parsing.

More like each thread is independent and simply blocking on a
completion port which when packet arrives "wakes" one of the thread to
process it and maintain the context until it's done.  No sense in
having one thread parse it and hand it off to another thread--saves
you a context switch.
